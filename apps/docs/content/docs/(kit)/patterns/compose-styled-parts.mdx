Each overlay in the kit comes in three layers. You can use the ready component, compose its styled parts, or render Kobalte yourself and take only the kit classes.
This page builds the same Line height popover each way. Start from the top and step down only when the layer above cannot express your layout.
[Choose ready components or parts](/docs/ready-or-parts) explains the layers in general.

## Use the ready component

<SolidDemo name="compose-styled-parts/ready" />

`Popover`, `PopoverTrigger`, and `PopoverContent` come from `@codeui/kit`. `PopoverContent` portals the panel and renders the title and the description for you.
Pick this layer first. You own the content and the state. The kit owns the arrangement, the IDs, and the ARIA links.

## Compose the styled parts

<SolidDemo name="compose-styled-parts/parts" />

The parts come from `@codeui/kit/popover`, or `@codeui/kit/dialog` for a dialog. Each part wraps one Kobalte primitive, adds the kit class, and sets a `data-cui` attribute.
Pick this layer when the ready component fixes something you need to change. Here the close button sits next to the title, which `PopoverContent` does not render.

You own the arrangement. Keep every part inside its `Root`, and keep `Title` inside `Content` so the panel still has an accessible name.
[Dialog](/docs/components/dialog#build-a-custom-layout) shows a larger example, a settings dialog with a breadcrumb title and two panes.

## Kobalte with kit classes

<SolidDemo name="compose-styled-parts/styles" />

Here Kobalte's `Popover` renders every element, and `popoverStyles` from `@codeui/kit/popover` supplies the classes. The trigger takes its class from `buttonStyles.button`.
Pick this layer when you need a Kobalte option or element that no kit part exposes, but still want the kit look.

You own the composition and the `data-cui` attributes. Copy them from `popoverParts` or `dialogParts`, so CSS and tests that target a part still match.
Install `@kobalte/core` as a direct dependency of your app before you import it.

## Pick a layer

| You need | Use |
| --- | --- |
| A standard dialog, popover, or menu | The ready component |
| A different arrangement of the same parts, such as an extra close button or a two-pane body | The styled parts |
| A Kobalte part or option the kit does not wrap, with the kit look | Kobalte with `*Styles` classes |
| A different look altogether | Kobalte alone, with your own CSS |

## Override kit styles with plain CSS

<SolidDemo name="compose-styled-parts/override" />

Every kit rule sits in the `cui` cascade layer. Unlayered CSS in your app wins over a layered rule, whatever the stylesheet order.
So one class on `PopoverContent` widens the panel and adds padding, with no `!important` and no extra specificity. The same holds for a class on a part or next to a `*Styles` class.

A CSS reset is the exception, because an unlayered reset also wins. [Cascade layers](/docs/foundations/cascade-layers#keep-app-resets-below-cui) shows how to put the reset in a layer below `cui`.

## Style components inside a toolbar

The toolbar sets the layout and chooses the variants of the controls it renders. Each control supplies its own base styles, focus styles, and interaction states.

<SolidDemo name="compose-styled-parts/editor-toolbar" />

```css title="editor-toolbar.css"
.editor-toolbar {
	display: flex;
	flex-wrap: wrap;
	align-items: center;
	gap: var(--cui-space-3);
}

.editor-toolbar__save {
	margin-inline-start: auto;
}

.editor-toolbar__line-numbers [data-cui="switch-control"] {
	margin-inline-end: var(--cui-space-1);
}

.editor-toolbar__status {
	flex-basis: 100%;
	margin: 0;
	color: var(--cui-text-hint);
	font-size: var(--cui-font-size-caption);
}
```

`theme="primary"` gives Save the kit's primary treatment. The `editor-toolbar__save` class pushes that instance to the end of the row. A selector such as `.editor-toolbar [data-cui="button"]` would also match Reset and any buttons nested inside future toolbar children.

To style a part of a ready Switch, pass `classes={{ control: "line-numbers-track" }}` when you can set its props. With styled parts, pass `class="line-numbers-track"` directly to `Switch.Control`. Both give the track a class you can target directly.

When the integration gives you access to the root alone, scope an Anatomy selector to that instance. The demo puts `editor-toolbar__line-numbers` on the Switch root and targets `[data-cui="switch-control"]` beneath it. The selector matches the track in both checked and unchecked states. [Switch anatomy](/docs/components/switch#anatomy) lists the part names.

For color or geometry, set a documented CSS custom property on the component or part where you want it to take effect. Set it on a shared ancestor when the entire subtree should inherit it. [Change one instance](/docs/foundations/theming#change-one-instance) shows a token override on a Button.
